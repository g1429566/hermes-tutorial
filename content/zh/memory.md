### 先观察一次忘记

你在一次对话里说：“以后默认用中文回答，只有我明确要求时才改用英文。”接着询问一个问题，Hermes 用中文回答。这还不足以证明它建立了长期记忆，因为这句话仍在当前对话里。

现在结束这个任务，用 `/new` 开始一个新会话，再问一个无关的问题。如果新会话仍能遵循这项偏好，需要有一条跨越会话边界的信息通路。Hermes 的内置持久记忆就是其中一条通路。

先明确三个时间单位。一次**迭代**是主循环里的一次模型请求及其后续处理；一个**回合**是用户发出一条请求，到 Hermes 完成这次回应，中间可能有多次迭代；一个**会话**可以包含许多回合。重启程序可能恢复旧会话，不能把“重启”直接当成“新建会话”。

### 保存在哪里与读取了什么是两个问题

模型每次回答依靠本次请求中的上下文。上下文包括系统说明、对话消息以及这次请求附带的工具定义等。硬盘上保存了资料，不代表这份资料已经进入了本次模型请求。

例如，你的电脑里保存了上周的日志文件，但模型没有收到文件内容，也没有调用读取工具，就不能凭空知道日志中的某一行。记忆文件、历史数据库和技能文件同样如此：每种存储都需要明确的读取时机。

我们先按实际对象区分四种信息，再看可选扩展。

| 信息对象       | 适合保存什么                                   | 什么时候进入当前上下文                               |
| -------------- | ---------------------------------------------- | ---------------------------------------------------- |
| 当前会话消息   | 用户刚才的要求、这一轮工具结果、尚未完成的工作 | 作为当前会话的一部分随模型请求发送；过长时可能压缩   |
| 内置持久记忆   | 跨任务仍适用的少量稳定事实、用户偏好           | 启动会话时读取记忆文件，形成系统提示中的快照         |
| 会话历史数据库 | 以前讨论了什么、具体报错、当时选择某方案的理由 | 恢复会话或调用 `session_search` 搜索、读取所需历史时 |
| 技能文件       | 完成某类任务的步骤、判断条件、易错点和验证方法 | 用户调用技能，或 agent 按需查看技能时                |

“工作记忆、情景记忆、语义记忆、程序性记忆”可以帮助类比这些用途，但它们不是 Hermes 中一个统一对象的四个必经处理阶段。初学时先能判断信息存在哪、怎样读出来，比先背四个名称更有用。

### 内置记忆由两份文件组成

Hermes 为内置记忆提供两种目标。

`USER.md` 保存关于用户的稳定事实，例如语言偏好、沟通方式，以及用户明确表达的长期要求。`MEMORY.md` 保存跨任务有用的环境事实或通用约定，例如用户明确指定的长期工作目录。属于某类工作的完整操作流程应写入技能，避免挤占每次会话都会读取的空间。

两份文件位于当前 profile 的 `<Hermes home>/memories/`。在采用默认路径的 POSIX 安装中，通常是 `~/.hermes/memories/`；其他平台、自定义目录、命名 profile 的实际位置可能不同。查看当前 profile 和其 home 后，再检查相应文件。

默认容量分别为 `MEMORY.md` 2,200 字符、`USER.md` 1,375 字符，可以在配置中调整。这里的单位是字符，不能把它们直接当成 token 数。模型使用 token 计量输入，字符与 token 的对应关系随语言和模型而变。

为什么容量这么小？因为这些内容在新会话中会自动出现。放入一份长日志，会使许多与该日志无关的任务也背上这段输入。少量稳定事实适合常驻，细节适合按需读取。[实现依据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool_store.py)

### 走完一次保存与读取

本例假设内置用户画像已启用，写入不需要等待审批，当前 profile 中没有这条偏好。

1. 会话 A 启动。Hermes 读取已有记忆文件，此时 `USER.md` 没有语言偏好；系统提示中的记忆快照也没有。
2. 用户在 A 中说：“以后默认用中文回答，只有我明确要求时才改用英文。”这句话首先是一条普通用户消息。
3. 模型判断它是值得长期保留的用户偏好，调用 `memory` 工具，将一条简短事实写入 `target: user`。
4. 工具实际成功后，磁盘上的 `USER.md` 出现这条事实。工具结果也让当前回合知道写入是否成功。
5. 当前 A 的系统提示快照保持原样。A 仍可以从刚才的用户消息和工具结果知道这项偏好。
6. 用户创建新会话 B。B 读取更新后的 `USER.md`，在自己的初始快照中看到这项偏好。

用一张状态表核对关键区别：

| 时刻             | 磁盘文件     | A 的初始记忆快照            | 当前消息中的新信息       |
| ---------------- | ------------ | --------------------------- | ------------------------ |
| A 刚启动         | 没有语言偏好 | 没有语言偏好                | 没有                     |
| 用户提出长期偏好 | 仍未保存     | 没有语言偏好                | 有用户的明确要求         |
| 工具成功保存     | 有语言偏好   | 仍是原来的快照              | 有要求及保存结果         |
| B 启动           | 有语言偏好   | A 的快照不会因 B 启动而变化 | B 的初始快照现在包含偏好 |

关键是区分**持久化**与**快照刷新**。持久化指把信息保存到磁盘，供以后读取；快照是某个时刻读出的固定副本。写入磁盘并不要求立即重建正在使用的副本。

如果另一个会话 C 早于保存动作就已经启动，它也不会仅因文件变化而自动获得新的初始快照。需要明确刷新或建立新会话，不能只等待几秒钟来假定它已更新。[快照实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool_store.py)

### 为什么保留旧快照

长对话的前半部分通常重复出现在后续请求里。部分模型服务能够复用已经处理过的相同前缀，减少重复计算，这称为提示前缀缓存。

如果每次写一条记忆都重新拼系统提示，就会改变请求靠前的位置，使后面的已有前缀更难复用。Hermes 因此把“学习结果保存到文件”和“这次会话继续使用什么系统提示”分开处理。

这不会让模型忘记刚才说过的话：刚才的话仍在当前消息中。它只是避免为了一次保存动作反复重写早先的上下文。缓存失效也没有固定的费用倍数；实际成本取决于供应商、模型、命中范围和输入长度。

### memory 工具怎样编辑条目

模型调用 `memory` 时必须提供两个顶层字段。`target` 选择要修改的存储（`user` 或 `memory`），`operations` 列出要对它执行的操作。每个操作用 `action` 指定新增（`add`）、局部修改（`patch`）或删除整条（`remove`）。只写一条时，列表里就放一个操作。会话启动时会读取记忆，模型还可以在写入结果中看到当前状态。[工具参数定义](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool.py#L398)

保存本例偏好时，模型提交的参数可以是：

```json
{
  "target": "user",
  "operations": [
    {
      "action": "add",
      "content": "用户默认希望用中文交流，明确要求英文时改用英文。"
    }
  ]
}
```

这是模型交给工具的参数，用 JSON 格式书写。外层大括号包住这次调用的字段。方括号表示列表，里面的一个对象描述一次新增操作，其中 `content` 是要保存的文字。

另设一个独立示例，假设用户已明确提供两项长期偏好，并实际保存为“用户默认希望用中文交流；报告日期注明时区。”后来用户说：“默认改用英文，其他偏好不变。”在原条目唯一匹配的条件下，可以只替换其中一段：

```json
{
  "target": "user",
  "operations": [
    {
      "action": "patch",
      "old_text": "默认希望用中文交流",
      "content": "默认希望用英文交流"
    }
  ]
}
```

结果是“用户默认希望用英文交流；报告日期注明时区。”日期约定没有被删除。`patch` 保留未匹配的其他文字。工具优先选择整条文字与 `old_text` 完全相同的条目。如果没有整条匹配，且该片段命中多条不同内容，或者它在选中的条目内重复出现，就需要加上周围的文字以确定目标。要删除整条过时记录则使用 `remove`，其匹配短语用于定位整条记录。[当前工具实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool_store.py)

旧教材中的 `replace` 有不同语义：它用新内容替换整条匹配条目。当前工具已经不向模型提供这个动作，继续调用会得到改用 `patch` 的提示。因此跟读旧版源码时，不能照搬新版动作；阅读新版教材时，也不能把 `patch` 当成旧式整条替换。

### 保存成功不能只看一句确认

“好的，我记住了”只是一段模型输出。它可能没有伴随工具调用，也可能对应一份等待审批的提案。判断是否已经保存，要看实际工具结果和存储内容。

如果启用了 `memory.write_approval`，交互式 CLI 的前台写入可以要求现场确认，其他场景的写入通常进入待审批队列。当前版本的无人值守后台复盘对修改或移除已有记忆还有额外限制，可能即使总开关关闭也先暂存。`staged` 表示待处理，不能解释成已经写入。

查看待审批项使用 `/memory pending`；选择一项后可用 `/memory approve <id>` 或 `/memory reject <id>` 处理。这里的 `<id>` 要替换成实际显示的标识。审批前先读完整目标和拟修改内容。[写入控制依据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/website/docs/user-guide/features/memory.md#controlling-memory-writes-write_approval)

### 容量满了怎样处理

内置记忆不会为了容纳新信息，悄悄删除旧条目。超出容量的写入会报错；模型需要检查已有内容，压缩重复表达，修正或移除过时事实，再保存有价值的新内容。

下面用一个不涉及真实字符计数的例子说明选择。假设文件已有两条：“用户长期使用中文交流”“用户的首选交流语言是中文”，又要保存“用户要求日期写明时区”。先合并重复语言偏好，比随机删除日期约定更合理。合并后还要检查是否真的满足该文件的容量限制。

需要同时整理和新增时，把针对同一个 `target` 的多个操作按顺序放进同一份 `operations` 列表。工具检查所有操作完成后的总容量，全部通过才提交。这样，最后的新增超出容量时，前面的删除也不会单独生效。修改另一份文件需另发一次调用。[容量与批次实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/memory_tool_store.py)

### 历史搜索怎样补上细节

假设你没有把上周的调试过程提炼进记忆，现在问：“上周处理 CSV 编码问题时，我们最终用了哪个编码？”简短记忆未必保存了答案，但会话历史可能仍保留当时的消息和工具结果。

`session_search` 搜索的是保存的会话记录。FTS5 是 SQLite 的全文检索能力，可以理解为数据库给文字建立的关键词索引。模型先用相关词找候选，再根据返回的会话和消息位置读取上下文。没有结果时，可以调整关键词或时间范围；不能把“没搜到”推成“从未发生”。

当前工具按参数区分几种用途：带 `query` 时发现相关会话；给出 `session_id` 时读取某会话；再给出消息锚点时查看附近窗口；没有搜索条件时可浏览近期会话。它返回已有记录及相关元数据，搜索本身不要求再调用一个 LLM 来编造摘要。

命中旧记录也不代表记录中的判断至今正确。上周的服务地址可能已迁移，模型需要把历史事实与当前状态分别核验。历史搜索还受当前 profile、显式选择的读取范围及可见性规则约束；“在同一台机器”不等于所有会话默认互通。[历史搜索实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/session_search_tool.py)

### 外部记忆 provider 放在什么位置

需要更丰富的检索或用户建模时，可以安装并配置外部记忆 provider，例如 Honcho 一类后端。provider 是能力提供方，在这里表示一套具体的记忆存储与检索实现；它不同于提供模型推理的 model provider。

Hermes 通过 `MemoryProvider` 接口与这些实现配合：准备用户回合时获取相关上下文，回合结束后同步需要保存的内容，在真正结束会话或关闭时处理相应生命周期工作。外部检索可以产生新的当前回合上下文，不应理解成每次重写主会话已有的系统提示。

不同插件可以采用向量、图、关系库或其他机制，并有各自的数据存放位置、网络依赖和费用。内置文件记忆与外部 provider 是可以分别配置的机制；没有安装外部 provider，也能使用内置持久记忆。[接口与回合接入](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/memory_provider.py)

### 动手核验一次跨会话记忆

先完成第 01 章的命令行安装。profile 是一套独立的配置和用户数据。这里新建一个名为 `memory-lab` 的学习 profile，让它从空白记忆开始。

1. **在系统终端创建 profile。** 运行 `hermes profile create memory-lab`。若提示名称已存在，换一个新名字，并在下面每条命令里用同一个名字替换 `memory-lab`。
2. **为它配置模型。** 在系统终端运行 `hermes -p memory-lab model`。`-p` 指定本次命令使用哪个 profile。在向导中选择可访问且支持工具调用的模型服务，按提示完成认证并选定模型。
3. **开始会话 A。** 在系统终端运行 `hermes -p memory-lab chat`。出现 Hermes 聊天输入框后，输入 `/profile`。确认显示的名字是你的学习 profile，并记下它的 home 目录。
4. **请求一次长期保存。** 在聊天框发送“请用 memory 工具记住，以后默认用中文回答，明确要求英文时才切换。”检查工具执行结果。若弹出审批提示，读完条目再确认。若结果包含 `staged: true`，输入 `/memory pending` 查看提案，用 `/memory approve <id>` 批准相应项，把 `<id>` 换成它的实际编号，并查看批准结果。
5. **核对磁盘。** 用文件管理器打开第三步记下的 home 目录，进入 `memories`，用文本编辑器打开 `USER.md`，查找刚保存的偏好。若找不到，回到第四步检查实际写入结果和目标。如果工具提示用户记忆已关闭，可在另一个系统终端运行 `hermes -p memory-lab config get memory.user_profile_enabled` 查看设置。
6. **观察新会话。** 回到 Hermes 聊天框，输入 `/new`，再问“Give me one tip for naming a file.”，观察回复使用哪种语言。然后要求“这次请用英文回答同一个问题”，观察它是否按你的要求切换。记录磁盘条目和两次回答，分别作为保存和行为的证据。模型本身也可能恰好选择中文，单次回答只能提供线索。

[创建和使用 profile](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/website/docs/user-guide/profiles.md#quick-start)

### 先预测再核对

**题目一。** A 和 C 已经启动。A 成功保存了新语言偏好，随后 B 启动。哪一个会话的初始记忆快照包含这次新写入？

**题目二。** 用户只说“这份报告请用英文”，是否应该把长期语言偏好改为英文？

**题目三。** 要找某次调试的具体报错，应该先向 `USER.md` 添加整段日志，还是搜索历史？为什么？
