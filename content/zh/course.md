# Hermes 教程正文

从一次可核对的任务开始，逐步理解工具、技能、记忆与自动化。纸上推演只使用给定条件；本机操作需要实际安装；界面模拟不会操作你的真实 Hermes。

## start Hermes 怎样完成一个任务

Hermes 是一个能够调用工具执行任务的个人 AI agent。这里把 agent 理解为围绕目标反复“判断下一步、执行、观察结果”的程序。语言模型负责根据已有信息提出下一步，Hermes 负责组织对话、提供工具、执行调用并把结果交回模型。工具使它能读取文件、运行命令或访问外部服务；工具是否可用，取决于当前配置和运行环境。

模型本次收到的信息叫上下文。系统提示提供任务之外的一般说明与行为规则，对话消息记录用户要求、模型回复和工具结果。Hermes 还会随请求提供可用工具的结构说明。资料只存在硬盘上而没有被读取时，不会自动成为模型这次能看到的上下文。

先看一个教学演示。文件中有三笔支出：早餐 12 元、午餐 28 元、晚餐 25 元。用户要求：“读取这份账单，计算总额，并告诉我怎么算的。”模型不能只根据文件名猜金额：它先请求读取文件，运行时返回三条记录，再计算 `12 + 28 + 25 = 65`，最后回答总额 65 元。计算可以通过可用的执行工具完成；这一过程的要点是结果来自实际读取的数据。

这与一次只生成文字的问答多了一条闭环：提出工具调用、观察执行结果、据此继续。模型提出调用，不代表调用已经执行；读到了内容，也不代表任务已经验收。后面会把这条闭环逐步拆开。

Hermes 还能把少量稳定事实保存为长期记忆，把已确认的工作流程整理成技能，再在以后的任务中读取。这里的“自我进化”指持久知识与操作指导的积累和修订；效果需要验证，不能理解成每完成一个任务，模型就自动训练一次。

**纸上推演：** 如果读取账单失败，模型是否仍有依据回答“总额是 65 元”？先判断，再核对：没有。它应处理读取失败，或明确当前无法获得账单；不能把演示中的数字当成真实文件内容。

## map 沿着一条请求认识仓库

打开仓库时，不必先记住所有目录。先跟着上一章的账单任务走：用户从某个界面输入请求，agent 核心准备上下文并请求模型，工具层读取文件，执行结果回到核心，最后由原界面展示回答。

入口可以是经典 CLI、TUI、桌面应用或聊天平台。CLI 是在终端输入命令和文字的界面；TUI 也是终端界面，但提供更完整的面板与交互；消息网关把 Telegram、飞书等平台协议转换成 Hermes 能处理的消息。多个入口可以驱动同一套核心，但各自还要管理输入、会话选择、审批展示和输出格式。

核心入口 `run_agent.py` 暴露 `AIAgent`，具体回合阶段分散在 `agent/turn_*.py` 等模块。`model_tools.py` 与 `tools/registry.py` 配合完成工具发现与分发；`toolsets.py` 定义工具组合；`tools/environments/` 负责终端命令的执行后端。`hermes_state.py` 及其同名前缀模块管理会话存储。

“门面与同主题模块”是一种代码组织方式：门面保留外部使用的入口，细节按主题拆开。因此查某个功能时，先定位主题和函数，再看门面如何调用它，不要默认所有逻辑都在最大的入口文件里。

**自检：** Telegram 中显示的换行有问题，和文件读取工具返回了错误内容，应先查同一层吗？参考判断：前者先查平台格式与适配器，后者先查文件工具、执行目标与参数；二者都经过 agent 核心，却不一定由核心逻辑造成。

## features 按任务认识能力

功能表的用途，是帮助你决定完成一个任务需要哪些能力。以“每天汇总销售 CSV”为例：读取和计算依靠工具；稳定的处理步骤可以写进技能；定时启动依靠调度；推送到聊天平台依靠网关；默认语言偏好可以进入内置用户记忆。只有任务确实需要这些步骤，才需要相应配置。

再看“今天临时算一次总额”。这时普通会话和读取、执行工具通常已经够用，不必先建立定时任务或多 agent 系统。把可选功能全部开启，会增加配置和排错范围，并不会自动提升答案质量。

能力可以分成三组理解。第一组完成当前工作，包括文件、终端、浏览器及多模态工具；第二组组织工作，包括会话、委派、定时任务和看板；第三组保留可复用信息，包括内置记忆、历史搜索、技能与可选外部记忆 provider。它们可以配合，也可以单独使用。

本教程里的功能矩阵是学习地图，不是完整的实时产品清单。具体平台、模型和插件以当前版本的设置界面、帮助与官方目录为准。

**自检：** “把今天三笔支出求和，结果直接回在这里”至少需要哪几步？参考：取得三笔真实数据，计算并核对，返回结果。只有涉及文件时才需要文件读取，只有需要定时或外发时才引入调度与网关。

## install 安装并验证第一次对话

先区分安装入口。macOS、Windows 用户可以选择官方桌面包；只需要命令行时使用对应平台的源码安装器；Android Termux 使用专门的 APT 安装指南。下面明确以 Linux、macOS 或 WSL2 的命令行安装为例，Windows PowerShell 和 Termux 不直接套用 shell 配置步骤。[安装入口](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/website/docs/getting-started/installation.md)

第一步，在终端运行官方 POSIX 安装命令：

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

安装器准备 Hermes 及其管理的运行依赖。看到安装成功后，按安装器提示重开终端或重新加载对应 shell 配置；不清楚使用哪个 shell 时，直接新开一个终端窗口，比随意执行 `source ~/.bashrc` 更明确。

第二步，完成模型服务配置。运行 `hermes model`，选择可访问的 provider 与模型，并按该 provider 的向导完成认证。provider 是提供模型推理的服务方；模型是这次任务实际请求的具体模型。API 是程序请求服务的接口；API key 是其中一种认证凭据，有些 provider 使用登录或其他认证方式。

第三步，运行 `hermes doctor` 检查环境。诊断中若某个未配置的可选能力不可用，应先判断本次任务是否需要它；首轮文字对话不要求先接通全部平台与工具。

第四步，运行 `hermes` 进入交互式会话，发送“请用两句话说明你可以怎样配合我完成任务”。收到回答说明模型链路已经跑通。再发送 `/help` 查看当前入口支持的命令。要验证工具，还需在工具可用时单独测试一个读取或计算任务，不能把文字回答成功当成所有工具已就绪。

区分两种命令位置：`hermes model` 在系统终端运行，`/help` 在 Hermes 聊天输入框中发送。示例中的尖括号通常是待替换参数，不是需要原样输入的字符。

**故障判断：** 终端提示找不到 `hermes`，先检查安装结果与命令搜索路径；启动后认证失败，先检查当前 provider 的认证；模型回答成功而某工具不可见，再检查工具配置和依赖。三个问题发生在不同环节。

## agent-loop 一条用户请求为什么调用多次模型

用户发出一个请求到收到最终回应，称为一个回合。回合内部可能有多次模型请求，每次称为一次迭代。会话则可以包含许多用户回合。明确这三个单位，才能理解预算、记忆触发和持久化时机。

继续使用支出例子。初始上下文只有用户要求和工具定义：第一次模型请求提出读取账单；Hermes 执行读取，把三笔金额作为工具结果追加；第二次模型请求提出计算；执行工具返回 65；第三次模型请求根据结果形成回答。实际模型也可能合并步骤，本例只是便于观察的最小过程。

工具调用通常由名称、参数和调用标识组成。消息的角色标识来源：user 是用户，assistant 是模型，tool 是工具结果。工具结果需要关联原调用，模型才能知道哪个结果回答了哪个请求。一条 assistant 消息可以包含多个调用，后面跟多条 tool 结果。因此不要机械地把相邻两条 tool 消息判为协议错误。

例如，模型提出读取 A 的调用编号 1、读取 B 的调用编号 2，返回结果就要分别对应 1 和 2。即使 B 先读完，也不能把 B 的正文误当成 A。编号在这里用于关联，不表示工具内容天然可信或已经满足任务要求。

下面是教学伪代码，省略了错误恢复、流式传输、审批与存储，不是可直接执行的 Hermes 源码：

```text
准备当前回合的消息和工具定义
在预算允许且没有中断时重复：
    请求模型
    如果有工具调用：
        按运行时规则执行，并为各调用追加对应结果
        继续请求模型
    否则处理本轮文本结果并结束本回合
```

顺序推进的控制流，并不排斥一次模型请求使用流式响应，也不排斥同一批独立工具并行执行。流式响应表示内容分批到达，可以在完整结果生成前显示已到达的部分；并行表示多个允许独立进行的动作在时间上重叠。请求适配、工具执行和界面渲染分别有自己的职责。正常结束、达到预算、中断和请求失败也要区分；“没有工具调用”不自动证明用户目标已经完成。[执行依据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/tool_dispatch_helpers.py)

服务通常按 token 计量输入输出。token 是模型使用的文字或数据编码单位，不能固定换算成“一个字”。输入前半段保持相同时，支持前缀缓存的服务可能复用先前处理；这有助于减少重复计算，却不会让历史内容不再占上下文窗口。

**纸上推演：** 模型提了两次读取调用，只返回一个结果，能直接进入最终汇总吗？参考：先找缺失的调用结果或明确失败状态；不能把第二个文件当成已成功读取。进一步核对账单的三个数，才能验收 65 元的结果。

## skills-1 技能怎样指导工具

工具执行动作，技能描述怎样组织这些动作。`read_file` 可以读取文件，却不会仅凭工具名称知道这类销售报告应如何处理缺失值。技能正文可以规定：先看列名，再确认缺失规则，随后计算，最后报告有效条数和排除条数。

Hermes 技能以 `SKILL.md` 为入口。Markdown 是用纯文本写标题、列表等结构的格式，`.md` 是常见文件后缀。文件开头可以用一行 `---` 开始、另一行 `---` 结束，中间放 YAML frontmatter，也就是一组描述这份文件的字段；例如 `name: csv-report` 表示名称字段的值是 `csv-report`。这些元数据说明名称、用途及可选条件，后面的正文提供步骤和判断。元数据帮助发现技能，正文帮助执行任务，二者作用不同。

例如，教学技能 `csv-report` 的描述可以是“汇总销售 CSV，并核对缺失值与输出条数。”正文再写出输入条件、步骤和验收方法。这个名称只是本例取名，不表示你安装后一定自带同名技能。

完整过程是：启动或扫描时建立可用技能目录；用户调用技能或模型判断相关后读取正文；模型再依据正文选择真实工具；运行时执行调用并返回结果。技能本身不会绕过工具权限，也不会保证所需文件或服务必然存在。

`scripts/` 可以携带确定性脚本，`references/` 存放按需阅读的细节，`templates/` 存放输出模板。只有本次需要时才读额外材料，能减少无关输入。仓库贡献规范还对描述长度、署名和平台声明提出要求；这些要求与“YAML 语法能否解析”是不同层面的检查。[技能规范](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/prompt_builder.py)

**自检：** “每次收到 CSV 都自动执行脚本”能否仅靠把脚本放进 `scripts/` 实现？参考：不能。必须有触发路径、模型或调度发起执行，并具备工具和权限；文件存在只是可用资料的一部分。

## skills-2 策展器怎样维护技能库

技能库积累很多内容后，即使每个文件都语法正确，也可能出现长期不用、近似重复或过时的流程。curator 是技能库的维护机制。先把它与“任务结束后的经验复盘”分开：前者整理技能库，后者从当前经验提炼更新。

当前默认的确定性维护依据活动时间：满足检查时机后，超过 14 天无活动的受管技能可以标为 `stale`，超过 30 天可以归档。这些阈值可配置。`stale` 仍可使用；归档后的内容可以恢复，不等于物理删除。[策展机制](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/curator.py)

纸上推演时，先假设本轮检查已允许运行，技能都已过宽限期。技能 A 最近活动在 3 天前，B 在 20 天前，C 在 40 天前；三者都受管且未 pin。结果分别为保持活跃、标记 stale、归档。若 C 已 pin，就跳过自动流转。若技能由 cron 任务引用，还需考虑对应保护，不能只套天数公式。

使用次数不是质量分数。一个技能很久没用，可能只是业务低频；经常使用也可能仍含错误。需要内容质量判断时，结合验收和可选 LLM 整理；策展器的 LLM consolidation 阶段默认关闭，不应写成每次维护都会运行。

`created_by: agent` 在这里是明确交给策展管理的政策标记。前台应用户要求创建的技能不必自动纳入闲置归档；符合条件的技能可以显式 `adopt`。pin 保护归档相关行为，lock 用于限制 agent 改写内容，二者不能替代。

**自检：** 一个受管技能 40 天没使用，是否在第 40 天一定已经归档？参考：不一定。还要检查维护是否运行、是否 pin、是否受任务引用保护等条件。模拟按钮演示的是给定条件下的一次判定，不是现实调度器的完整时钟。

## tools 从工具定义到实际执行

模型看见的工具定义，通常包括工具名、用途和参数结构。参数结构也叫 schema，它告诉模型应当提交哪些字段、字段类型是什么。schema 描述动作，handler 是收到参数后实际运行的函数。

一个工具成为当前可调用能力，需要经过几个判断：实现是否已注册，工具组合是否选择了它，当前会话是否适用，以及必要依赖或配置是否可用。“文件在仓库里”“已经注册”“模型看得见”“执行成功”是四种不同状态。

以读取文件为例：模型提出 `read_file` 和目标路径，运行时定位 handler，检查必要条件并执行，再返回内容或错误。agent 级工具以及插件工具有各自接入方式，不能把所有调用都画成完全相同的一个函数入口。

再区分模型的建议与运行时的安排。模型可以在一次响应中提出读取 A、读取 B 两个调用；运行时可把适合并行的调用并发执行，并按原调用顺序整理结果。若先写 A 再读 A，就存在数据依赖；当前工具批处理还会考虑路径冲突和必须串行的工具。[并发与门控依据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/tool_dispatch_helpers.py)

toolset 是工具组合的名称，用于选择暴露给模型的能力。未暴露的工具不占这次工具清单；已经暴露的插件工具同样会带来 schema 输入成本。扩展能力时，先问已有工具或技能能否完成任务，再决定是否需要新增工具。

**纸上推演：** 读取互不相关的 A、B，与“修改 A 后核对 A”，哪组更适合并行？参考：前者通常独立；后者必须保证核对看见修改后的状态。是否真正并行还要满足工具运行时的准入规则。

## delegation 把子任务交给子 agent

委派适合把相对独立的子问题交给另一个 agent 上下文处理。例如，要比较两个互不依赖模块的接口，可以让两个子任务分别检查，父 agent 最后对照结论。父 agent 必须给出目标、所需上下文和交付格式；子 agent 不会自动拥有父对话的全部信息。

内置 `delegate_task` 为子任务建立独立的对话上下文和终端会话，运行同一套基本 agent 循环。子任务完成后，把结果交回父 agent，详细中间轨迹通常不会全部灌入父上下文。这样能控制父上下文的体积，但最终摘要也可能遗漏重要细节，父 agent 仍要核对依据。

这里的独立上下文不等于独立进程或独立文件系统。内置委派可以在线程池中执行；如果两名子 agent 对同一目录改同一个文件，仍可能冲突。需要隔离修改时，要另外安排不冲突的文件范围、目录或工作树，并选择适合的执行后端。[内置委派实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tools/delegate_tool_dispatch.py)

交互式会话中，委派可以先返回派发标识，随后在完成时将结果交回；一次性运行路径可能在调用内等待。调用返回了派发标识，只能说明已经派发，不能当作子任务已完成。并发、嵌套深度和子任务预算也都要受控。

**自检：** “分析模块 A”和“分析模块 B”可以并行；“设计接口”和“按最终接口实现”能否直接同时做？参考：后者存在依赖。可以先调研实现约束，但正式实现要等接口稳定，或接受返工代价；不能只因有多个 agent 就宣称依赖消失。

## gateway-1 消息平台怎样接到同一核心

Telegram、Discord、Slack、飞书的消息格式和连接方式不同。adapter 是适配器，负责把平台载荷转换成统一消息事件，并把回复转回平台支持的形式。这样 agent 核心不必为每个平台重写一次任务循环。

从用户发一条私聊消息开始看：平台收到消息，适配器解析文本和附件，网关确定属于哪个会话与 profile，核心执行任务，回复再根据来源送回。来源信息不仅是平台名，还可能包括聊天、线程、工作区等标识。

统一处理不等于所有平台共享同一份会话。两个用户、两个线程、两个 workspace 是否共享上下文，由会话归键和路由规则决定。共享或移交需要明确配置，不能仅因同一个 gateway 进程接收消息就推断互通。

接入一个平台也不仅是填 token。需要配置身份、验证连接、确认消息能进入目标会话，并检查回复、附件和控制操作在该平台的展示。新增平台优先使用提供的插件与平台注册接口，不在首页演示中鼓励直接修改核心网关。

**自检：** 两条文字相同的消息来自不同线程，是否必然进入同一会话？参考：不必然；应检查用于归键的来源字段。文本内容相同不能替代会话身份。

## gateway-2 一条消息如何排队与得到回应

一个会话正在执行任务时，又收到消息，网关需要决定它是后续任务还是控制动作。普通后续消息可以排队；停止、审批等控制操作必须能够及时到达处理器，否则可能出现“工具在等审批，而审批被排在工具后面”的等待循环。

按过程走一遍：第一条消息启动任务，运行时请求某项审批；用户提交审批选择；入站适配器识别控制输入，网关把它交给等待的审批路径；获得结果后继续或停止工具；最终回复回到原聊天。真实实现有多层忙碌检查，控制消息需要通过相关层的正确路径，不能只修改一个队列条件。

语音消息通常先经过 STT，也就是语音转文字，然后进入普通文本处理。TTS 是相反方向的文字转语音，两项能力分别配置。语音识别可能有错，涉及数字、姓名和指令时，需要保留核对或澄清机会。

跨入口继续会话还要区分恢复和移交。恢复读取已保存的会话；移交把会话关联到另一入口。能否在目标平台建立线程、是否配置了目标地址，都影响行为。同进程里可以存在 live 状态，跨进程重启只能依赖已经保存的状态，不能说重启后仍读取旧进程的内存。

**纸上推演：** 一个任务正在等用户审批，把用户的批准当成下一轮普通提示会发生什么？参考：当前任务继续等待，而下一轮又等当前任务结束，形成互相等待。控制信息必须送到正在等待它的对象。

## cron 到时间以后谁启动任务

定时任务先保存“什么时候运行”和“运行什么”，调度器再检查是否到期。保存计划不会立即执行，也不表示电脑关闭时仍有人替你运行；必须有相应调度进程和可用运行环境。

以每天生成一份销售汇总为例：先确认时区和每天 9 点的含义，保存调度与任务提示；到期后建立执行会话，读取指定输入、计算并核对，最后按配置保存或投递结果。任务提示里应写明输入在哪里、缺失值怎么处理、输出给谁，不能只留下“照昨天那样做”。

周期和一次性延时要分清。当前解析中 `30m`、`every 30m` 表示周期运行，`in 30m` 表示 30 分钟后运行一次。五字段 cron `0 9 * * *` 表示按调度时区每天 9 点；它依次描述分钟、小时、日、月、星期，不是“从现在起每隔 9 小时”。

错过执行、进程竞争和卡住需要不同机制。有界补跑处理错过的时间，任务认领或锁减少重复触发，空闲超时处理长时间没有活动，预算与迭代限制处理持续活动但没有完成的循环。没有一种超时可以替代所有约束。

**自检：** 现在 8:50，需要 9:20 提醒一次，应选 `in 30m` 还是 `30m`？参考：前者。随后再确认使用的时区及是否有运行中的调度器；表达式正确只是触发条件的一部分。

## kanban 看板怎样协调多个任务

当任务需要跨进程重启保留、等待依赖或分配给不同 worker 时，一块持久化任务板比一次临时委派更合适。任务板记录任务内容、当前状态、认领者及相关运行信息；worker 是实际执行任务的工作单元。

先设有两张卡：A“核对 CSV 字段”，B“按确认后的字段生成报告”。A 就绪时可以被认领；B 要等待 A 给出映射，不能因为板上有空 worker 就先跑。A 完成后，系统或用户根据依赖条件让 B 进入可执行状态。

多个 worker 同时认领 A，需要原子认领。原子表示“检查是否可领”和“写下已认领”作为一个不可被另一方穿插的状态变更完成，避免两者都以为自己拿到了同一任务。worker 停止报告活动后，还需要识别失效认领并决定回收或重派。

界面里把卡片从就绪拖到完成，只是在演示状态关系，不证明对应的真实工作已经完成。真实系统还要核对 worker 产物、失败原因、重试次数和依赖。board 与 tenant 的路由边界也应和操作系统、容器权限边界分开理解。

**自检：** worker 已写出报告，但在登记完成前崩溃，重派会不会重复写报告？参考：可能。认领避免的是同一时刻错误并领；重试还需要幂等处理或产物核对。幂等指重复执行不会额外产生错误的重复效果。

## tui 终端界面与后端怎样分工

TUI 是终端里的交互界面，负责显示消息、输入框、工具活动和审批提示。Hermes 的这套前端使用 TypeScript 与 Ink，Python 后端管理会话、模型调用和工具执行。经典 CLI 与 TUI 是不同界面入口，并不要求你把整个 agent 改写成 TypeScript。

两端通过 JSON-RPC 通信。JSON 是表示结构化数据的文本格式；RPC 是向另一端请求执行某项操作。一次请求包含方法、参数和标识，响应使用相同标识关联结果；事件可以报告消息增量或工具状态。

例如，用户提交提示，前端发送提交请求；后端调用模型，将增量文本作为事件送回；前端逐渐显示文字。需要审批时，后端还可以反向提出请求，前端展示选择并返回响应。因此通信不是只有“用户发文字、后端回文字”两个固定动作。

终端宽度实验帮助理解显示状态：同一段文字在 40 列和 80 列会折成不同的行，历史消息偏移可能需要重算。实验若按字符简化折行，应明确它没有模拟所有中文宽度、组合字符和终端控制序列。它解释布局思想，不等于真实终端排版算法。

**自检：** 后端持续送来了消息增量，但界面没有显示，首先怀疑模型没有生成内容是否合理？参考：先检查前端订阅、状态更新和渲染链路。事件已送达说明故障可能在显示层；仍要核对事件所属会话是否正确。

## cli 命令名称怎样变成行为

先分清系统终端命令和聊天斜杠命令。`hermes model` 由命令行参数解析入口处理，`/model` 由当前会话的命令分发处理。它们可能最终使用相同配置能力，但不是同一段输入在所有地方原样执行。

斜杠命令的公共定义可以记录名称、别名、说明、分类和入口条件。帮助、补全和菜单从同一份定义派生，能减少“帮助里有命令、分发却不认识”的不一致。定义名称之后，还必须有处理器实现行为。

以添加一个教学命令为例，顺序是：定义命令元数据，编写处理函数，连接相应入口，验证帮助与实际行为。若设置需要跨会话保留，还要写入正确 profile 的配置。注册表不能代替处理器，也不能让一个只适合终端的命令自动拥有聊天平台语义。

修改工具或技能可见性时，需要考虑当前会话已经使用的工具定义与系统提示。默认把持久设置留给后续会话，显式立即刷新则承担相应缓存影响。不能用一次配置写入推断所有已打开会话都已更新。

**自检：** 给命令添加别名后，菜单识别了新名字，但执行无效果，该检查什么？参考：核对别名是否归一到规范名、分发表是否命中处理器，以及入口条件和参数传递；“出现在菜单”只证明定义链路的一部分正常。

## backends 终端命令到底在哪台机器上执行

Hermes 的控制进程、用户看到的界面和终端执行环境可能在不同位置。例如，你在笔记本的界面发出请求，Hermes 后端在服务器上，而命令又通过 SSH 在另一台主机执行。判断某个文件是否存在，要问执行工具实际访问的是哪一处。

local 后端直接使用相应主机上的进程；Docker 使用容器；SSH 连接远端主机；云沙箱后端把命令送到相应服务。它们共享一套上层接口，但文件可见性、依赖、权限和生命周期不同。HPC 等场景还可以使用插件提供的后端。

以“读取 `data/sales.csv`”为例，在 local 下它相对于当前执行目录解析；切到 Docker 后，需要文件在容器里可见；切到 SSH 后，路径属于远端环境。主会话记得路径字符串，不能保证目标环境存在同一份文件。

休眠和快照主要解决资源生命周期与文件持久化。有的后端停止并恢复同一沙箱，有的从快照重建；文件保留不代表内存进程、网络连接和所有外部资源都原样恢复。费用还可能包括存储、网络和服务基础费用，不能只按“没有运行命令”推断成本为零。

**自检：** 笔记本上运行 `ls data` 能看见 CSV，能否证明 SSH 后端也读得到？参考：不能。应在实际执行目标核对目录和文件，必要时通过明确的挂载或传输准备输入。

## profiles profile 怎样隔离用户状态

profile 是一套独立的配置与用户状态范围。工作 profile 可以使用工作模型凭据、工作技能和会话，个人 profile 使用另一套数据。它主要解决状态归属，不等同于新建一个操作系统用户或安全容器。

先设 A 保存“工作报告默认中文”，B 保存“个人练习默认英文”。正确行为是进入 A 的新会话读取 A 的偏好，进入 B 读取 B 的偏好，再回 A 仍读取 A 的偏好。这个 A→B→A 推演，比只用一个 profile 测试更容易发现状态串用。

代码应通过 `get_hermes_home()` 获取当前作用域的目录。单次 CLI 启动可以在导入前选择 profile；一个后端同时服务多个 profile 时，还需要按请求或后台任务绑定作用域，不能把启动时的全局环境变量当作每个任务的身份。

记忆、技能、会话和凭据应按所属范围访问。用户显式选择跨 profile 读取时是另一条受控路径，不是默认继承。查看所有 profile 的管理操作也不同于读取当前 profile 的内容。

**自检：** 模块导入时记下 A 的目录，稍后处理 B 的任务仍使用该常量，会发生什么？参考：B 的数据可能被写进 A。目录应按实际作用域解析，后台线程和子进程也要携带相应作用域，不能只修前台页面。

## build-skill 写出别人能照做的技能

写技能的起点是一类重复任务及其验收方法。以 CSV 汇总为例，先定义输入是带列名的表格，输出包含有效数字之和和缺失条数，再列出确认列名、判断缺失、计算和核对四步。最后才把这些知识放入 `SKILL.md`。

最小教学文件可以这样开始：

```markdown
---
name: csv-report
description: '汇总销售 CSV 并核对缺失记录。'
---

# CSV Report Skill

用于对带列名的销售 CSV 生成可核对的汇总。

## Procedure

1. 确认数值列和缺失值规则。
2. 读取实际数据；遇到无法解析的非空数字时明确报告。
3. 按确认后的规则计算，并报告有效条数与缺失条数。

## Verification

输入 100、缺失、120 时，有效和为 220，有效条数 2，缺失条数 1。
```

这是用于解释结构的最小教学样例。真正提交到 Hermes 技能仓库时，还需遵守对应贡献规范，补齐前置条件、执行入口、平台声明和必要测试；元数据表单通过，也不能证明正文完整或实际任务通过。

应先检查已有相关技能，优先修订现有流程。把确定性逻辑写成随包脚本时，在正文说明输入、运行方式和验收；不要只给一份脚本而跳过模型如何找到和调用它。

**自检：** 描述完全合规，但正文只写“正确处理 CSV”，算合格的教学技能吗？参考：不足。读者还不知道怎样处理缺失与非法值，也没有步骤和核对关系；语法正确与操作知识充分是两项检查。

## build-tool 什么时候需要新工具

先判断任务能否由现有工具完成。若只是指导已有文件和终端工具按顺序处理 CSV，技能通常已经足够；若需要一个稳定的结构化服务接口，才进一步考虑工具、插件或 MCP。个人需求优先使用扩展机制，避免把专用能力直接加入核心工具面。

理解工具实现时，先把三部分分开：schema 说明参数，handler 执行动作，可用性检查决定必要条件是否满足。最小教学 handler 可以接收一段文字并返回 JSON 格式的结果；这适合观察注册与分发，却不代表值得为“回显文字”增加一个真实核心工具。

用生成器练习时，先检查参数名与类型，再看生成代码中的 handler 如何取得参数，最后模拟一个成功和一个失败输入。浏览器里的 Pyodide 执行的是教学代码与替代注册表，能验证函数返回值，无法证明真实 Hermes 已发现、选择并执行该工具。

接入真实环境还要验证注册、暴露、依赖、执行、结果回写等路径。若走通用插件，使用插件的工具注册接口；若维护内置工具，遵循核心注册与 toolset 规则，两条路径不要混写。

**自检：** handler 单独运行能返回正确 JSON，但模型看不见工具，下一步先改 handler 吗？参考：先查注册、toolset、会话适用性和可用性检查。输出函数正确，并不能证明工具已经进入模型请求。

## build-provider 模型 provider 怎样接入

模型 provider 接入至少涉及四件事：怎样认证，向哪个地址请求，提供哪些模型，以及如何把该 API 的消息和结果接入 Hermes。相同的“聊天”功能，不保证不同服务接受相同字段。

`ProviderProfile` 用于集中声明 provider 信息及相关行为。很多服务使用 OpenAI 风格的 Chat Completions，也有 Responses、Anthropic Messages 或其他传输路径。教材可以先用一种请求形状解释基本过程，但不能据此断言真实主循环只调用一种外部 API。

以教学服务为例：用户选择 provider，完成认证，读取模型列表，选择支持所需工具调用的模型，再执行一个最小任务。若目录获取失败，可以有兜底模型清单；清单能被选择，不证明账户已经有权限访问该模型，仍需真实请求验证。

还要核对流式输出、工具参数、reasoning 相关字段、图像输入和错误分类。认证成功只验证了链路的一部分。配置里非秘密行为参数与秘密凭据也要分别管理，不能把所有字段都塞进 `.env`。

**自检：** 普通文字请求成功，是否可以宣布 provider 已完整支持 agent？参考：不能。还需至少验证一次工具调用及结果回传；有多模态、流式或特定接口要求时，也要分别验证这些路径。

## build-plugin 插件怎样扩展 Hermes

插件把扩展能力放在核心之外。清单说明插件身份与类型，入口向 Hermes 提供的上下文对象注册工具、命令或其他能力。不同插件类别有不同接口，不能把所有插件都简化为“在六个钩子上挂函数”。

以一个读取项目统计信息的插件为例，先确认现有文件工具与脚本是否已满足需要。如果确实要提供专用能力，就通过通用注册接口声明它，并配置依赖和启用方式。插件本身不应为某个供应商偷偷改写核心源码。

生命周期钩子用于在已有阶段运行具体逻辑，例如观察工具调用结果。钩子的调用时机、返回值是否影响流程、错误怎样处理，都属于契约；不能看到有回调接口就假定可以任意改变会话历史。

插件可能在主进程或专用 host 进程运行。进程外执行有边界和不支持的对象类型，也不自动提供容器级文件访问隔离。启用前应按真实插件类型检查兼容性、配置和运行结果。

**自检：** 一个记忆插件希望增加功能，直接修改用户安装目录的 `run_agent.py` 是否合适？参考：应使用已有通用接口；确有通用缺口时，为该需求扩展公共接入面，而不是在核心中留下某个插件的特例。

## design-agent 从需求组合一套 agent

先写可验收的需求，再选组件。教学需求为：“每天读取指定目录的一份销售 CSV，排除缺失销售额，报告总额与缺失条数，默认中文，出现非法非空数字时停止并报告，结果回到指定聊天。”输入、输出、失败条件和投递目标都有了定义。

据此可以逐项组合：读取与计算用现有工具，报告流程用技能，默认语言用内置用户记忆，周期运行用调度，投递用配置好的平台入口。只有数据规模或任务独立性需要时，再加入委派；只有任务要排队、重试和等待依赖时，再考虑任务板。

部署选择还要回答数据在哪、命令在哪执行、谁持有凭据、谁运行调度、任务失败后谁能看见。控制进程位于本机，不代表文件工具也能自动读取云端；把后端迁到云端，也不会自动让笔记本文件变得可见。

完整设计卡应包含最小成功路径和至少一个失败路径。若 CSV 根本没有到达，系统应报告缺少输入，不能继续拿昨天的数据生成“今天成功”的消息。然后用固定样例验证各路径，而不是只评价组件选择是否像 Hermes。

**开放练习：** 如果只需今天人工触发一次，哪些组件可以省略？参考判断：通常不需周期调度；若直接在当前聊天回复，也不需额外投递通道。保留真实读取、规则明确和结果核对，说明省略后的能力边界即可。

## interview-loop 怎样解释 agent 循环的设计

面试回答先说明任务中的依赖，再描述控制流。例如：“读取结果决定怎样计算，计算结果决定最后回答，所以一个回合可以按迭代顺序推进。独立读取可以在一批中并行，模型响应也可以流式处理。”这样比“同步一定比异步简单”更准确。

接着解释消息为什么要保留工具调用和结果的配对，以及为什么稳定的早期上下文有利于前缀缓存。新消息追加在尾部不必破坏已有前缀；主动重建早期内容可能影响复用。上下文压缩则是容量压力下的有意取舍，并不是免费操作。

最后补上退出路径：任务有最终结果、预算或迭代到限、用户中断、请求失败分别怎样处理。不要把预算到限时的收尾回答视为任务必然成功，也不要宣称中断只是设置一个标志、永远不影响正在执行的工具；实际还涉及请求取消、工具状态和结果整理。

**练习：** “既然控制流按顺序推进，为什么还能并行读取两个文件？”先回答再核对：顺序描述的是阶段依赖；工具执行阶段内部可以并发，随后按调用标识和顺序收集结果，两者并不冲突。

## interview-multi 怎样选择多 agent 协作方式

协作模式是分析任务关系的概念，不是五个必须打开的 Hermes 功能开关。Manager 由一个协调者拆任务再汇总；Handoff 按阶段交接；Supervisor 对产物检查并给出反馈；共享任务板协调多名 worker；大量同类独立任务还可由 worker 从队列领取。

先给依赖画箭头。比较两个模块可以并行调研，写完方案再实施是顺序依赖，写作与审校是带反馈的循环。选结构时同时问：谁持有全局目标，谁看到哪些材料，谁决定完成，失败能否重试，重试是否会重复产生副作用？

Hermes 的内置委派能支撑父子协作，看板能持久化任务状态。但“失败到次数就 block”只是一项失败控制，不等同于有语义质量标准的 supervisor；给 cron 配上游输出也不必然建立“上游成功才触发下游”的完整工作流。

有依赖就按依赖安排，有反馈循环就设验收与停止条件。不要以“100 个任务”直接推出必须使用某种模式；任务时长、资源上限和人工协调成本都影响选择。

**开放练习：** 为“收集资料→写报告→按引用检查后修订”设计协作。参考：可以用顺序交接加有上限的审校循环；给出中间产物、验收标准和最多修订次数即可。单 agent 分阶段执行同样可能满足需求，要说明多 agent 的额外收益与成本。

## interview-design 把选择写成系统设计文档

设计文档要让未参加讨论的人理解系统怎样满足需求。先写用户、输入、输出、规模与约束，再画出成功路径，然后展开状态存储、接口和失败处理。每个组件都应能回应一项需求，不能只堆流行名词。

以销售汇总为例，需求不是“上一个 memory、再接一个 swarm”，而是“每天在指定时区得到可核对的汇总”。工具解决动作执行，技能解决流程复用，记忆解决跨任务稳定偏好，调度解决触发，看板是否需要则取决于持久排队与协作要求。

数据部分要说明每个对象的生命周期：会话消息何时持久化，记忆何时读取，技能何时更新，任务卡何时认领和释放。再写一个真实失败例子，比如报告已经投递但完成状态没保存，重试怎样避免重复通知。

最后定义评测：正确总额、正确缺失条数、异常报告、是否重复投递、耗时和成本。不能只写“系统可靠”，要给读者可检查的关系与条件。

**自检：** 文档里写“独立上下文，所以数据完全隔离”有什么缺口？参考：还没说明文件系统、凭据、数据库和执行环境的边界。上下文隔离只是其中一个对象的隔离。

## interview-checklist 用可观察表现做自评

“读过”和“能解释”之间还有距离。每个主题用三项表现自评：能用自己的话说明对象和机制；能在给定条件下走完一次过程；能在条件变化后修改判断。标记完成是学习记录，不是能力证明。

以记忆为例，先解释当前上下文与文件记忆的区别，再推演 A 保存、B 新建时的状态，最后回答“另一个已启动的 C 是否自动刷新”。如果只会背 MEMORY.md，却不能解释 C 的行为，薄弱点在读取时机。

以工具为例，解释 schema 与 handler，再推演注册到执行的链路，最后改变一个条件：“依赖缺失”“路径不在实际执行环境”“已注册但未暴露”。根据结果定位缺失环节，才说明理解可以迁移。

建议把一段口头回答或纸上轨迹留作自评依据。答错时回到具体缺口，补完再做变式，不把“翻过答案”直接计为掌握。

**练习：** 不看教材，用五句话解释内置记忆、历史搜索与技能分别解决什么；再举一条不该长期保存的信息。参考判据是用途、读写时机和边界都正确，而不是使用了多少英文术语。

## reliability 按失败类型选择处理办法

先确定故障在哪一层。模型请求暂时限流、输入超过上下文窗口、工具参数错误、用户停止任务、持久化失败，是不同问题。对所有问题都立即重试，可能只增加成本或重复副作用。

暂时性网络问题可以按规则重试；明确无效的参数需要修正；过长输入需要减少或压缩；用户中断应停止相应工作并整理已完成状态。429 也有不同原因，不能一见 429 就断言账户余额为零；要按错误分类与 provider 的实际状态处理。

工具失败可以变成模型可读的结果，让模型决定下一步。但这不等于失败已经补偿。例如外部发送操作可能成功了，只是响应丢失，再次发送就会重复；需要查询状态、幂等标识或其他可核对机制。

空闲超时处理没有进展的等待，墙钟限时处理总运行时长，迭代或 token 预算限制连续消耗。一个不断输出却没有完成目标的循环可能不会触发空闲超时，需要其他停止条件。日志帮助复盘，审批帮助表达授权，二者都不能保证所有错误被阻止。

**纸上推演：** 工具因参数缺失失败，原样重试三次会解决吗？参考：没有依据。先补齐缺失参数，再决定是否重试。若错误是“发送结果未知”，还应先查状态，避免重复操作。

## interop 用参与方区分互操作协议

先问哪两端在通信，再选协议。Hermes 自己的界面与后端使用内部 JSON-RPC 方法；编辑器驱动 agent 可使用 ACP；agent 调用外部工具与读取资源可使用 MCP；独立 agent 服务之间交换任务可使用 A2A。相似的 JSON 外形不表示它们承担相同职责。

MCP 描述工具、资源等能力接口，传输可以包括 stdio 或 HTTP，具体按服务实现与配置。MCP server 的内部可以调用普通函数、数据库，也可以调用一个 agent；协议本身不限定服务内部必须或不得包含模型循环。

ACP 关注编辑器与 agent 的会话、请求和权限交互；A2A 面向独立服务的任务与产物交换。进程内临时子任务通常先考虑内置委派，不必为所有协作都引入跨服务协议。Hermes 的具体 MCP server 插件发布方式应按当前目录核对，不能继续引用已经不存在的旧 catalog 文件。

**选择练习：** 编辑器里向 Hermes 提交修改请求、给 Hermes 接一个数据库查询工具、给另一个独立 agent 服务派任务，分别先研究什么？参考：ACP、MCP、A2A。若只是给 Hermes 写自己的桌面界面，则研究 Hermes 内部前后端契约。[协议定位依据](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/tui_gateway/contracts/)

## compression 对话太长时怎样继续

上下文窗口是模型单次请求能处理的输入与输出范围。前缀缓存可以减少重复处理，却不会把窗口变成无限大。随着历史和工具结果增长，系统仍需要控制输入体积。

先做便宜的处理：避免无关的大结果进入上下文，超长材料保留必要片段或可读取的引用。仍有压力时，上下文压缩用更短的表示保留目标、已确认结果、待办和继续工作所需信息。摘要会丢细节，因此要设计保留范围和核验方法。

纸上设历史包含“目标：统计有效销售额”“已确认缺失值排除”“已读取三个文件”“某文件有非法值未处理”。一个只写“已经处理销售文件”的摘要就丢掉了待解决问题；更合适的摘要应保留规则、已完成范围和具体未完成项。判断摘要好坏，看后续是否还能正确行动，不看文字是否流畅。

文件 checkpoint 保护的是另一种状态：在启用且操作受支持时，为相关文件变更准备可恢复快照。它不能把已经发送的消息、远端数据库或所有运行进程一起撤回。上下文压缩、会话恢复和文件回滚要分别说明。

**自检：** 摘要生成成功，是否能保证所有历史细节都没丢？参考：不能。应检查继续任务必需的信息，并在需要时读取历史证据。文件回滚也无法补回摘要里省略的推理信息。

## routing 主模型与辅助模型怎样选择

先区分三类动作。同一 provider 内更换凭据，解决某个凭据不可用；切到备用模型或 provider，处理更广的可用性问题；给标题、压缩、视觉或复盘指定辅助模型，则是在任务层选择执行者，不一定是故障降级。

以主模型被限流为例，运行时先根据配置和错误分类判断能否重试或换凭据；仍无法继续时，再看是否有配置好的 fallback。备用模型也可能有不同上下文长度、工具和视觉能力，切换不能被描述成完全无差别。

辅助任务配置解决另一种需求：你可以让主模型完成复杂分析，让适合的辅助模型生成标题或压缩。压缩模型首先要装得下待压材料并能保留关键事实，价格低并不是唯一条件。

阅读路由图时，按当前版本解释优先级，不把某个固定 provider 列表写成永久规律。配置存在、认证有效、模型可访问、任务能力适合，要分别核对。

**自检：** 配了一个廉价备用模型，是否能保证大上下文视觉任务无缝继续？参考：不能。要验证备用模型的窗口、视觉和工具支持，以及消息转换路径；可用性和能力等价是不同条件。

## multimodal 图片与语音怎样进入任务

多模态表示请求或结果不只有文字，也可能包含图片、音频等内容。Hermes 可以把部分能力封装为工具或 provider 扩展，但这不表示核心消息始终只有纯文本；支持原生视觉时，请求中可以包含图像内容块。

例如，用户要求解释一张销售图。若主模型支持对应图片输入，可以由主模型直接分析；否则可由辅助视觉路径生成分析材料，再交回当前任务。识别图表数值仍可能出错，涉及准确计算时应优先获取原始表格并核对。

图像生成与图像理解也不同：前者产生新图，后者解释已有图；图像编辑需要源图和明确变更。不同生成 provider 的参数、费用、等待时间和输出形式不同，不应只靠“有 image_url”概括所有路由。

语音输入常经 STT 转成文本，语音输出由 TTS 把文字转成音频。把识别文字当作用户意图前，需要考虑转录错误；例如“十五”和“五十”对金额计算有实质影响。

**自检：** 图片里看起来是 50，识别结果却是 15，后续计算能靠 agent 循环自动保证正确吗？参考：不能。需要核对图像、原始数据或向用户澄清，循环本身不会提供缺失的真实证据。

## evaluation 怎样测量 agent 是否变好

先定义成功，再安排批量执行。对 CSV 教学任务，至少测有效和、缺失条数、非法值处理与解释是否符合要求。只测模型是否输出文字，会把格式完整但数据错误的答案也计为成功。

准备多份固定输入，每份附预期结果和可用工具条件。运行时记录模型、配置、技能版本、完成状态、工具调用、耗时与成本。独立会话不应无意共享可变状态，否则前面的任务可能改变后面的条件。

batch runner 负责按配置批量执行、保存结果并支持相应恢复；评测器负责判断结果是否满足标准。程序能从断点继续，不代表崩溃前已经发生的外部副作用都能自动撤销。轨迹保存的是任务过程，可以供分析或后续训练流程使用，但保存轨迹本身不会训练模型。

验证自我进化时，固定模型和任务设置，对照加载修订前后技能的结果，再使用未参与技能修改的输入。报告样本数、失败类型和成本变化，不只报“新增了几个技能”。

**纸上练习：** 更新后两次求和都对，但遇到非法数字时仍悄悄跳过，能否说该技能完全通过？参考：只能说已展示的求和用例通过，异常处理还失败。下一步应定位该规则的缺口，用独立变式再次核验，而不是增加一个“已学会”的计数。
