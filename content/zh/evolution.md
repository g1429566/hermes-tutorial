### 自我进化具体改变什么

第一次整理 CSV 时，Hermes 可能需要查看列名、确认数字格式、处理缺失值，并根据用户反馈调整输出。下一次做类似任务，如果它能加载一份经过修订的流程，就可能少走一些弯路。

在这里，“自我进化”具体指保存和修订持久记忆、技能及其辅助资料，使未来任务获得更合适的上下文和操作指导。这条运行时路径不要求训练或修改基础模型的权重。模型权重是模型内部通过训练得到的参数；修改磁盘上的 `SKILL.md`，改变的是未来读到的指令内容。

因此要用三个问题判断是否真的发生了积累：改变了哪份持久内容？下一次怎样读取它？读取以后，有没有改善任务结果？一次回复中说“我已经学会了”，无法单独回答这三个问题。

### 用一个完整例子看经验怎样提炼

教学任务是汇总一份 CSV 中的销售额。输入如下：

```text
日期,地区,销售额
2026-11-01,华东,100
2026-11-02,华南,
2026-11-03,华东,120
```

用户要求：“只汇总有效销售额；缺失值不要擅自补 0，在结果里告诉我排除了几条。”这个要求给出两种输出：有效数字之和，以及被排除的缺失条数。本例有效和为 220，排除 1 条。

假设 Hermes 第一次把缺失值补成了 0。虽然本例求和碰巧仍然得到 220，处理方式已经违反要求；如果下一次算平均值，错误会更加明显。这说明判断任务成功，不能只核对一个总数。

用户指出补 0 的问题，Hermes 按要求重算，报告有效和 220、有效 2 条、排除 1 条。至此，它只知道这份报告该怎样处理。接着 Hermes 问：“以后为你汇总这类销售报告，也按同样的规则处理缺失值吗？”用户确认：“是的，以后都默认排除缺失销售额并注明排除条数。如果某次要补 0，我会在那次说明。”

有了这句确认，Hermes 才能把约定写进销售报告技能，让以后的同类任务读取。如果用户没有确认长期约定，仍可提炼一条通用步骤，即每次汇总前先确认缺失值规则。

### 从输入到下次复用的六个环节

第一步是**获得反馈**。反馈可以来自用户纠正，也可以来自工具结果、测试或验收标准。本例的反馈不是“模型觉得答案不错”，而是缺失值规则和输出的可核对关系。

第二步是**判断信息去向**。跨任务语言偏好进入 `USER.md`；当前任务的一次性中间值留在历史；CSV 处理步骤和该类报告的约定进入技能。不要把同一事实复制进所有存储来假装更可靠。

第三步是**查找已有技能**。如果已经有 CSV 报告技能，先阅读当前内容和相关资料，定位导致错误的步骤。只有现有技能无法合理容纳这类任务，才考虑新建；文件更多不等于知识更好。

第四步是**写入可执行的修订**。用 `skill_manage` 修正原有步骤，写清适用条件、操作顺序和验收方法。涉及支持文件时，把脚本、模板与相对引用作为完整技能包处理。按写入策略，这次动作可能直接生效，也可能等待审批。

第五步是**让未来任务读取**。技能的简短描述帮助模型判断相关性；正文在用户调用或 agent 按需读取时进入上下文。已经写到磁盘的内容，并不会自动替换当前会话中较早读过的那一段。新会话重新读取，是最容易核对的路径。

第六步是**在变式任务上验证**。换一份含两个缺失值的 CSV，核对有效和、有效条数、排除条数。只有能按新的输入继续正确处理，才能说这条经验至少在这些条件下有用。[经验组织与写入实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/prompt_builder.py)

### 技能应该怎样写这条经验

下面是教学用技能正文节选，不是某份真实技能的源码原文：

```markdown
## Procedure

1. 读取列名并确认本次要汇总的数值列。找不到销售额列时先确认映射，不按列位置猜。
2. 确认缺失值规则。此类报告默认排除缺失销售额并报告排除条数；用户本次另有要求时按本次要求处理。
3. 只对可解析的有效数字求和。无法解析的非空文字单独报告，不当作缺失值悄悄跳过。
4. 输出有效数字之和、有效条数与缺失条数，注明所用规则。

## Verification

对 100、缺失、120，结果应为有效和 220、有效条数 2、缺失条数 1。
另用包含非空非法数字的输入，确认系统会明确报告问题。
```

这里保留了能指导下次执行的内容：输入条件、规则、步骤和核对关系。没有保留“星期一第几次尝试失败”等事件叙述。那类细节仍可从会话历史追溯，没必要让每次使用技能都重新读一遍。

### 前台学习与后台复盘

**前台学习**发生在当前任务中。用户可以直接要求“把确认过的做法更新到现有技能”，模型在处理这次请求时调用 `skill_manage`。保存动作及结果属于当前可见任务。

**后台复盘**在满足条件的回合结束后，使用一份对话快照检查是否有值得保存的记忆或技能经验。它运行自己的 agent 分支，不把“请反思并学习”偷偷插进正在交付给用户的主消息流。分支在这里表示独立运行的上下文副本，不是 Git 分支。[后台复盘实现](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/background_review.py)

“后台”不等于“每回合必然新建技能”。当前实现通过不同计数器判断是否需要复盘：记忆提醒按用户回合累计，技能提醒按工具调用迭代累计，相关默认间隔为 10。达到阈值还要满足工具可用、自动复盘开启、回合正常结束等条件。某些有限运行或无人值守路径会跳过自动复盘。是否值得写入仍需模型判断，结果也可能是没有可保存内容。[触发条件](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/turn_finalizer.py)

这个差别很实用：一个用户请求可能执行了很多轮工具调用，即使聊天只发生一个回合，也可能达到技能复盘阈值。反过来，一连串简短闲聊不一定产生值得整理的操作流程。

### 后台复盘怎样与主对话并存

后台分支拿到一份快照，以自己的运行状态审阅，保存结果写到相应存储。主会话已有的系统提示、工具定义和旧消息不因为它想保存经验就被重建。

同模型复盘可以复用与主会话一致的已有前缀，但缓存能否命中仍取决于服务端。改用另一模型时，无法假设同样复用，当前实现会采用较紧凑的对话材料。复盘仍会消耗模型请求和 token，需要把它算进运行成本。

为限制后台分支的行动范围，运行时在执行侧使用工具白名单。即使为缓存一致性保留了与主会话相同的工具定义，实际允许调用的也只是相应的记忆、技能及必要读取工具；配置允许的额外工具还需满足已有工具面的条件。由此可以区分“请求里描述了工具”和“这条运行路径获准执行工具”。[分支与白名单](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/background_review.py)

### 学错了怎样发现与修正

假设一次浏览器调用因临时网络超时失败，第二次重试成功。合理经验可能是：遇到这种超时，先核对网络状态，按既定重试策略再试。错误经验则是：“浏览器工具不能用，以后禁止使用。”

第二种表述把一次环境状态变成永久约束。以后环境已经恢复，模型仍可能引用这条技能拒绝工作。因此复盘应保存有证据、已确认、可迁移的规则；没有找到有效办法的失败尝试，不能包装成推荐流程。

发现错误记忆时，修正或删除对应条目；发现错误流程时，修改误导性的原步骤，再用一个变式任务验证。不要在原错误后面不断追加“更新：其实……”而让下次模型同时读到相互冲突的规则。

### 用哪些开关控制学习

这些控制针对不同对象，不能互相替代。

| 控制项                                | 主要控制什么                      | 不应据此推断什么                 |
| ------------------------------------- | --------------------------------- | -------------------------------- |
| `memory.write_approval`               | 内置记忆写入是否要求审批          | 不等于关闭历史存储或技能写入     |
| `skills.write_approval`               | agent 对技能的写入是否要求审批    | 不等于禁止读取已有技能           |
| `auxiliary.background_review.enabled` | 是否自动发起回合后的复盘          | 不等于禁止前台明确保存或手动复盘 |
| `curator.enabled`                     | 是否启用技能库的后台策展维护      | 不等于关闭内置持久记忆           |
| `curator.consolidate`                 | 是否启用策展器的 LLM 内容整理阶段 | 不等于控制逐回合的学习复盘       |

要查看待处理提案，分别使用 `/memory pending` 和 `/skills pending`。想主动整理刚才的经验，可使用当前版本支持的 `/refine`，并写明希望检查哪类经验。学习轨迹可通过 `/journey` 或 `hermes journey` 查看；看到“新增技能”记录仍不等于技能已经验证有效。[复盘命令](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/website/docs/reference/slash-commands.md)

还有一个面向材料整理的入口 `/learn`：用户明确提供文档、项目目录或刚才确认过的做法，让当前 agent 阅读材料并整理可复用技能。它与 `/refine` 的重点不同：前者从指定来源学习，后者主动复盘经验；两者最终仍要通过读取、判断和实际写入才能产生持久变化。

例如，你已完成并核对了上面的 CSV 任务，可以发送：“`/learn` 把刚才确认的销售 CSV 汇总方法整理到相关技能，保留缺失值规则和核验样例。”接下来检查实际技能写入结果；有待审批项就先处理，再开新会话加载该技能做变式。不能在输入 `/learn` 之后立刻假定下一次任务已经使用新流程。[学习入口](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/website/docs/user-guide/features/skills.md#learning-a-skill-from-sources-learn)

### 策展器负责维护积累后的技能库

第 09 章的 curator 解决另一件事：技能越来越多时，怎样避免长期不用的内容一直挤在目录里。

它读取活动记录，在满足空闲与检查间隔的维护时机，执行确定性的闲置流转。当前源码默认在无活动满 14 天时可标记为 `stale`，满 30 天时可归档；这些是可配置阈值，检查到期时才执行，不是每个技能在第 14 天整点自动改变。`stale` 仍可使用，归档移到可恢复的目录。

这套判断使用活动时间，不是任务准确率评分。一个冷门但重要的技能可能很久不用，一个错误技能也可能频繁被查看；所以“常用”与“正确”必须分别判断。

默认策展只管理明确交给它托管的技能，相关记录使用 `created_by: agent` 标记。标记表示维护政策，不是历史作者证明。`pin` 保护符合条件的技能不被自动归档；如果要阻止 agent 改写技能内容，使用 `lock`。可选的 LLM 整理默认关闭，开启后可以整理重复内容，但仍受保护和审批规则约束。[策展器与托管政策](https://github.com/NousResearch/hermes-agent/blob/9302ba9e212c63ba24cdf1f47f26b47bcd3b042e/agent/curator.py)

### 怎样判断自我进化有没有帮助

不要只统计生成了多少技能。技能数增加，可能意味着记录了有用经验，也可能意味着重复和噪声增加。

对 CSV 例子，可以准备三份教学输入：一份没有缺失值，一份有缺失值，一份有非空非法数字。固定任务要求与允许的工具，比较更新前后是否正确求和、报告异常，以及用了多少轮工具、耗时和 token。记录模型和配置，避免把更换模型的收益误算给技能更新。

还可以暂时不加载该技能进行对照。即便结果改善，这也只支持“在这些样例和条件下有帮助”，不能据此断言所有 CSV 任务都会变好。真实项目还需要未参与技能修改的输入，检查经验是否过度贴合某一个样例。

### 自检与反馈

**题目一。** 一次报告要求按部门排序，是否应该立即把“所有回答按部门排序”写进 `USER.md`？

**题目二。** `skill_manage` 返回待审批，但模型说“新流程已生效”。哪一处证据应当优先？

**题目三。** 一个技能 40 天没有使用、已经 pin，但没有 lock。可否从中推出 agent 不能修订它？

**题目四。** 同一模型在新会话里读了修订后的技能，完成任务更好。模型权重是否必然改变了？

<details>
<summary>尝试后核对</summary>

第一题：不能。先确定它是这次报告的要求，还是这一类报告的长期约定；即使是后者，也应写入相关报告技能，而不是提升成所有任务的默认规则。

第二题：以真实工具结果为准。待审批还不是已应用，后续任务不能假设文件已经改变。

第三题：不能。pin 与编辑锁是不同保护。pin 保护归档相关行为；要限制 agent 改写内容需要相应 lock，并结合具体写入策略判断。

第四题：没有这个必要。技能改变了新会话的输入，就足以影响行为。这是上下文与持久知识的更新路径。
